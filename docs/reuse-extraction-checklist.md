# 再利用ルール（切り出し判定チェックリスト）

このドキュメントは、他プロジェクトでも使える資産を見つけたときに、  
「調査 -> 切り出し -> テンプレ保存」まで迷わず実行するための運用ルールです。

## 使い方（毎回この順番）

1. 候補を1つ決める（例: クロスフェードPopup、見積ステップ制御）
2. 下の「切り出し判定」を YES/NO でチェックする
3. YES が多い場合は `Core` として切り出す
4. 実装後は「保存前チェック」を通してテンプレへ反映する

---

## A. 切り出し判定（Go / Hold）

### A-1. Go 条件（3つ以上で切り出し推奨）

- [ ] 2案件以上で再利用する見込みがある
- [ ] 業務文言や固有データを外しても成立する
- [ ] 入出力（props / data contract）が説明できる
- [ ] 単体で動く最小デモを作れる
- [ ] バグ修正を1箇所に集約したい価値がある

### A-2. Hold 条件（1つでも当てはまれば要注意）

- [ ] 特定顧客の業務フローに強く依存している
- [ ] APIキーや外部環境がないと動かない
- [ ] UIではなく運用ルール依存が大きい
- [ ] 仕様が頻繁に変わっていて安定していない

---

## B. 分類ルール（どこに置くか）

### Core（テンプレ本体）

汎用ロジック。業種や業務が変わっても使えるもの。

例:
- ページ遷移モーション
- Popup切り替え
- 遅延表示制御
- 質問再表示判定（`shouldAsk`）

### Domain Pack（差し替え前提）

業務ごとに差し替える設定・ルール。

例:
- 質問項目
- 文言
- 単価・重み
- プロンプト

### App Adapter（接続層）

既存アプリとの橋渡し。CoreとDomainを結合する層。

例:
- handoff decode/encode
- 画面遷移時のURL・session連携

---

## C. 調査チェックリスト（実装前）

- [ ] 依存ファイルを列挙した（import元/利用側）
- [ ] 副作用（router, storage, window, fetch）を洗い出した
- [ ] 入力と出力を型で定義した
- [ ] 既存テストまたは手動確認シナリオを決めた
- [ ] 既存画面の挙動を壊さない移行順を決めた

---

## D. 実装チェックリスト（切り出し時）

- [ ] ハードコードを減らし、注入可能にした
- [ ] 既存呼び出し側に互換レイヤーを残した（必要なら）
- [ ] 最小サンプルページを追加した
- [ ] READMEに「どこを差し替えるか」を追記した
- [ ] Lint / Build が通ることを確認した

---

## E. 保存前チェック（テンプレ反映）

- [ ] `含まれるもの / 含まれないもの` をREADMEに明記
- [ ] 新案件の「最初の5分手順」を更新
- [ ] デモルートの動作確認（最低1往復）
- [ ] 破壊的変更がある場合は移行メモを追加
- [ ] コミットメッセージに「なぜ切り出したか」を記載

---

## F. 判断に迷ったときの原則

- 迷ったら **Coreを小さく**、Domainを厚くする
- 先に「再利用可能な最小単位」で出す
- 最初から完璧な汎用化を狙わず、2回目の再利用で磨く

---

## G. 30秒クイック判定

次の問いにすべて YES なら切り出してよい:

1. 別案件でも同じ問題を解くか？
2. 業務文言を消しても価値が残るか？
3. 使い方をREADMEに5行で書けるか？
